# s39-t1 — the door: a drop folder that carries a render across

**Status:** STOPPED -- needs Colby: the door's live proof has to run on his Mac. Will you start the watcher in its own terminal and send one request through, as the two commands in *Next* below show? The container half is s39-t2; this task's code is finished, green and reviewed.

**In one paragraph:** the door is a shared folder with three subfolders and a rule: only data crosses it. The container writes a file naming a share code; a watcher on the Mac picks it up, renders it with `render_course --fresh` out of a copy of traxgen that only Colby updates, and writes the outcome back. The container never names what runs, where it runs from, or where the answer is written. That last one is the finding of this task: the first version validated the share code -- the field I was thinking about -- and left a second field, the request's `id`, feeding straight into a file path on the Mac. A hostile container could have written its result over any `.json` file Colby owns. Two reviewers who did not write the code found it independently, before it ran anywhere. The id now comes from the filename, which `glob` has already confined, and the body has no id at all. 68 tests and 21 mutants hold it. The one step left is the live proof, and only Colby can run it.

## Open (written before the work)

- **Goal:** build the drop folder that lets work running in a container ask Colby's Mac to render a share code, and get the result back, without the container ever choosing what runs there.
- **Scope:** `scripts/render_door.py`, `tests/test_render_door.py`. The `TASK-OPEN s39-t1` ledger line is the record.
- **Budget:** 60 minutes, three full test runs, zero renders (no emulator here).
- **Done check:**
  1. *Step:* building the door.
  2. *True after:*
     - the client writes a request as one file under `requests/`, carrying a share code and nothing else that reaches a command;
     - the watcher refuses any request whose code is not a ten-character share code, and refuses it without running a render;
     - for an accepted request the watcher runs `render_course --fresh` out of the Mac's own checkout, named by its own configuration rather than by the request, and writes the outcome, the exit code and any device-evidence path into `results/`;
     - the client returns that result for the same id, and returns a distinguishable outcome when no watcher ever claimed the request and when a watcher claimed it and died.
  3. *Miss cases:*
     - the watcher runs a render for an accepted request but would also have run for a code carrying a path, a flag or a shell metacharacter — the door then carries code, not data, which is the one property that made this option the pick;
     - a result file exists and the tests pass, but nothing asserts the watcher built a real `render_course --fresh` command, so a stub reads the same as a render;
     - the checkout the watcher renders from comes from the request rather than from the watcher's own configuration;
     - a request is claimed and abandoned, and the client blocks forever instead of reporting the door down;
     - a request is never claimed because the watcher is not running, and the client reports that as a render failure rather than as an absent watcher.
  4. *Reads:* the `pytest` run's own output; the argument list the watcher builds, captured by the test's fake runner; and the files left in `requests/`, `claimed/` and `results/` after each test, which the test creates before it asserts on them. None of these is this task's own account of itself.
  5. *Check:* `uv run pytest tests/test_render_door.py -q` reports every test passing and names how many; among them, one test asserts the watcher calls no runner for each of a list of rejected codes; one asserts the built argument list names the watcher's configured checkout, the `render_course` module and `--fresh`, and contains the share code as one whole argument; one asserts an abandoned claim returns a door-down outcome within the timeout rather than blocking; and one asserts an unclaimed request is reported as no watcher.
- **Outcomes declared before any live run:** none, because there is no live run. The door's live proof — a request crossing from a real container to the real Mac — needs Docker Desktop and Colby's hands, and is this task's stop.

- **The defect the panel found, recorded because it is the point:** the first version read the request's `id` from the JSON body and interpolated it into the result path. `Path.__truediv__` discards its left operand when the right is absolute, so `{"id": "/Users/colbykauk/.claude/settings"}` wrote the door's result over that file, while the watcher printed that it had *refused* the request -- the write sat outside the if/else, so the rejected path was the better one for an attacker: instant, and no render in the log. A `..`-and-absolute check would not have been enough either, since the container owns `results/` and could plant a directory symlink there. I had validated the field I was thinking about and not noticed there was a second one.

- **Decisions made inside the task:**
  - A request's identity is its filename, and the body has no `id`. `glob("*.json")` cannot return a name crossing a separator, so the confinement is already done before any path is built; a second source of truth for the same fact is what let the first version trust the wrong one. Every path is still checked to land inside the drop folder, and each subfolder is checked not to be a symlink on every use -- a `results -> ~/.claude` symlink defeats resolve-and-compare, because resolving under it lands outside and still looks contained.
  - The watcher catches `Exception`, not `OSError`, per request. `json.JSONDecodeError` subclasses `ValueError`, so a 15-byte malformed file killed the whole watcher before this. A boundary process the container can take down at will is not a boundary.
  - Requests over 4 KB are refused unread, and one pass serves at most 32. Neither is gold-plating: the container writes into this folder by design, so both are its cheapest attacks.
  - Everything the watcher prints goes through `!r`. The watcher's terminal is the human's only view of this boundary, and this project's standing note is to trust only harness-verified results -- a channel the container can forge with `\x1b[2K` is exactly that note's failure mode.
  - A filename that is not a request id is moved to `rejected/` under a name this module chose, not left in place. Left in place it is re-globbed every pass, and 32 of them would starve the queue. Nothing is deleted.
  - `--checkout` is required, with no default, so the request cannot name where the render runs from and a typo cannot silently point it at the working copy.
  - `--drop` is required when `TRAXGEN_DOOR_DROP` is unset. It was defaulting to `Path("") or None`, and `Path("")` is `PosixPath(".")`, which is truthy -- so the "required" guard was dead code and a stray `request` from the repo root created `requests/` inside the checkout. The epistemics reader caught this by running it.
  - `Result.from_json` drops unknown fields and coerces `stderr_tail` back to a tuple. JSON has no tuples, so the plain `Result(**json.loads(...))` handed the container a list while the dataclass promised a tuple; and a watcher one version ahead would have thrown `TypeError` at the client.
