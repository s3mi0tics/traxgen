# traxgen — Observations

Patterns noticed about how you and Claude work together on this project — frictions, recurring habits, things worth not losing. Numbered cumulatively across sessions; the numbers are stable references, so don't renumber when an observation moves.

This file has two sections. **Candidates** are patterns still being validated. **Promoted** are the ones durable enough to count as baseline expectations — a candidate promotes after it fires roughly three times across separate sessions (adjust the threshold in `workflow.md` if that doesn't fit your tempo).

A separate path runs to `decisions.md`: when an observation hardens into a commitment that constrains future work, it becomes a locked decision there, with the originating number noted for lineage. The two paths are independent — an observation can promote within this file, get locked as a decision, both, or neither.

**Update protocol.** The capture cadence lives in `workflow.md`; this file just holds the results. At session close: add new candidates, note any that fired again, promote the ones past the threshold, and retire candidates that have gone several sessions without firing.

## Promoted

1. **Integration canaries catch what synthetic unit tests miss.** Validating a real parsed fixture (GDZJZA3J3T, unlimited inventory) on every validator-rule commit has caught two real rule bugs that per-rule unit tests passed. Baseline expectation: any new rule ships with the canary green.
2. **Probe first, implement second.** When schema semantics are unknown, a small probe script against real fixtures beats reasoning from the spec — the retainer-family probe (fb2e547), the world-coord probe (3865bcb), the tile-index investigation, and the v7 byte-trace each settled a question that prose analysis had stalled on. Fired 4+ times. Stopping rule (refined 2026-07-22 from agentic-workflow-notes): probe until the next probe wouldn't change what you write — M6.a needed one probe, M4's retainer work needed many; the difference is whether each probe updates what gets built. **Fired again 2026-08-18:** the committed `trace_both.py` byte-dump plus upstream `skytrax.rs` settled the v7 layout after two wrong prose models of it in one hour — the first shim guessed the splice from the plan's summary and drifted 4 bytes per tile; the bytes and the Rust said what actually moved. **Fired again 2026-08-21 (s22), on a design dispute rather than schema semantics**: whether the probe's `table` rival should point at corrected `graph.py` was settled by panel agents *enacting* the alternative in a scratch copy — 13 failures, plus the run-builder dying at fresh positions — in minutes, after argument alone had already produced one false justification. Probes settle disputes about designs, not just formats.
3. **App-built oracle fixtures are the ground truth of last resort.** Building a course in the real app and fetching its bytes via murmelbahn's `/api/course/{code}/raw` resolves format questions definitively — used for GDZJZA3J3T, 4YCV8JHLX7, and X3WEQ6F296; the last of these broke the rail-model question wide open.
7. **Tooling-first is the working style — flag automation before the third repetition.** If a manual flow involves more than ~3 repeated clicks/pastes/drags that will recur, stop and build the tool, even at a 20–30 minute detour — and Claude proposes this proactively rather than continuing the manual walk-through. Declared explicitly and demonstrated across M6.c (screenshot shell function, tap harness). Folded 2026-07-22 from `docs/refs/agentic-workflow-notes.md`.
8. **Multi-edit patch scripts with exact-match validation are the default for doc edits.** "Old must match exactly once" catches both drifted text (0 matches) and over-generic text (N matches); sed silently does neither. Validate against the *evolving* text, not a pre-pass on the original — a separate pre-validation phase breaks chained edits (discovered 2026-07-22 when this very fold-in aborted on its first run). Fired in M6.a, twice in M6.c, and throughout the migration. **Fired again 2026-08-18** — mid-chain, the exact-match assert caught that ruff's autofix had already rewritten a target string (0 matches on text that existed one command earlier); validating against the evolving text is precisely what caught it.

19. **A verdict function can assert more than its own design guarantees.** **Fired twice more on 2026-08-21, both in code written that day while citing this observation in its docstring — which is the finding.** (a) `probe_plate_membership.classify()` demanded exactly one surviving model, while `build_cells()` only ever guaranteed that *some* pair of rivals is separated. Three firings total. **Original firing:** the starter-rotation sweep's `classify()` fired the right branch on the right trigger and then printed a mechanism its own run refuted. 15. **The upload endpoint fails transiently under batch load.** **Fired a fourth and fifth time 2026-08-23 (s23), with a new signature and a worse blast radius.** Not HTTP 520 this time but `_ssl.c:993: The handshake operation timed out` — and in a **standalone probe**, which had no auto-resume, so two failures in seven cells voided the entire campaign. The two that failed were the certified control and the local control, i.e. exactly the cells that make the other five mean anything; the five that rendered were consistent with the model and had to be discarded anyway, which is the bracket rule doing its job under temptation. A second run failed the same way. The fix moved the queue's designed-for policy into the library as `upload_course_with_retry` (`decisions.md`, s23), retried by exception class so a 4xx is not retried into a slower no, with attempt counts recorded into the sidecar — because this observation's value is the *count*, and a silent retry would erase the very signal that promoted it. Five firings in five batch runs makes this the endpoint's baseline behaviour, not an incident. **Fired a third time 2026-08-10** — one cell of the s=2 sweep, mid-queue, during an unattended run; the queue's auto-resume closed it without a human present, which is the first time the recovery path ran with nobody watching. Three firings in three batch runs makes this the endpoint's normal behaviour under load, and it is now a *designed-for* condition rather than a surprise: `run_sweep_queue.py` treats `INCOMPLETE`-with-no-abort as mechanical and repairs it automatically. **Fired again 2026-08-08**: one cell of 43 returned HTTP 520 mid-batch, in a different position from the first, and the resume path closed the hole in a single render 40 seconds later — the design held exactly as intended. Two firings in two batch runs suggests this is the endpoint's normal behaviour under load rather than bad luck, and that any sweep longer than ~40 cells should expect at least one. Original entry: one cell of 42 returned HTTP 520 (Cloudflare edge, not a payload rejection) mid-batch on 2026-08-07. Recoverable only because uploads run as a batch *before* renders and `upload_error` is recorded as a field distinct from a missing verdict — so the run reported `INCOMPLETE` rather than classifying on a hole. Argues for keeping the upload-all-then-render-all ordering rather than interleaving. Two firings.
16. **Exonerate the obvious suspect before diagnosing.** When `ime_ok` stopped working the intuitive cause was a stale tap coordinate; one `uiautomator dump` ruled it out (`[2216,252][2384,378]` contains (2270,305)) and redirected the entire diagnosis to timing. 17. **Guard the failure that invents data, not just the one that loses it.** **Third firing 2026-08-21, and it widened the lesson: a guard calibrated on one failure's *signature* does not cover the failure *mode*.** The plate-membership probe's first run rendered the app-certified control and got `inactive`. The screenshot was the Android **home screen** — GraviTrax was never in the foreground, because `render_course()` starts tapping at the main menu and never launches the app, while `assert_emulator_ready()` checks the emulator rather than what is in front of it. The 2026-08-07 frame guard could not see it: it refuses *near-white* frames (splash 0.942 vs renders 0.013–0.014), and dark wallpaper sits in the same range as a real render. Wrong *moment* was guarded; wrong *application* was not. What makes this the sharpest firing is what the run was testing — the probe predicted its two discriminating cells dark, so a harness aimed at the launcher returns precisely the all-inactive result that reads as a flawless confirmation of the hypothesis under test. The certified control is the only thing that stopped it: the 2026-08-07 both-ends lock earning its keep against a failure nobody imagined when it was written. The payload was byte-identical to the course that had rendered `active` in all six historical sweeps and deduped to the same share code, which exonerated the geometry in one command (#16's shape). Promoted the same day into a design rule — `decisions.md`, "Every render run carries a control at the position under test." **Prior firing 2026-08-10, and that time the guard was the only thing watching.** A locked screen throttled the occluded emulator; a fixed-sleep render sampled a loading screen at `white_frac` 0.653. Without the frame guard the oracle would have returned a brightness-driven verdict into an unattended run and no human would have seen the frame — the screenshot is pruned unless it is a failure or an active. Instead it raised, the cell was recorded as a hole, and one auto-resume closed it. The 2026-08-07 lesson (weight guards by what a wrong answer would be *believed* to mean) compounds under automation: unattended runs remove the human who would have noticed. Two firings. The 2026-08-07 harness failed twice in opposite directions. The IME desync made the oracle return `inactive` for a keyboard — a null result, which reads as "no finding" and costs a re-run. The splash screen made it return `active` — a *positive* result, which reads as a discovery and would have been recorded as `MODEL_WRONG`. Same oracle, same magnitude of bug, wildly different blast radius. When ranking guards, weight by what a wrong answer would be *believed* to mean. One firing, but it determined which fix shipped first. **Fourth firing 2026-08-23 (s23), and this time the guard was the one working.** The opening certified control of the interior probe was refused at `white_frac 0.660` — a loading screen — so the run reported INCOMPLETE and no verdict rather than a brightness reading. It cost one re-run and invented nothing. The same session closed the *other* half of the third firing's lesson: the s21 launcher failure was wrong-application rather than wrong-moment, and `assert_app_in_foreground` now guards that axis directly instead of hoping a brightness threshold covers it. Worth stating plainly, because it is the shape of this whole entry: the frame guard and the foreground guard are two different questions, and each was discovered only by the failure the other could not see.
18. **A pre-declared threshold is only as good as the model behind it.** The sweep's image-diff check was pre-declared as "a few percent of the frame" for a real difference; the real answer was 0.07%, because the camera sits far enough out that a two-tile course occupies a sliver of the frame — a fact not known when the number was chosen. Declaring it early was still right: it forced an escalation to direct inspection instead of allowing a post-hoc rationalisation in either direction. The lesson is not "don't pre-declare" but "pre-declare the *decision procedure*, and treat a missed threshold as a trigger to look harder rather than a verdict." One firing.
20. **Reproducing the record is not evidence; only prediction is.** **Fired again 2026-08-10, on the winning side.** With s=2 and s=3 measured, parity (even → {E, NW}, odd → {NE}) was stated in conversation as an explicit forward prediction for s=4 and s=5 *before* their renders ran — and both landed. Same discipline as the 2026-08-08 firing, opposite outcome, which is what makes the pair informative: the rule earns belief by surviving a declared test, not by fitting the rows behind it. Also the reason `graph.py`'s table refuses to interpolate even now that all six rows exist — a pattern that survived prediction is still a pattern, not a mechanism. Two firings. The parity model was encoded as a test that replays all 42 previously-rendered cells, and it passed every one — then missed one of its four forward predictions on the very next run. A model built from a dataset explains that dataset by construction, so a green replay says nothing about correctness; it only guards against later edits silently breaking an old observation, which is a real but much smaller job. Worth keeping both, and worth not confusing them. One firing.
21. **Before running an experiment, ask what a null result would prove.** Fired twice on 2026-08-08. The handoff proposed sweeping the starter against a *mispredicted* cell (NE rot 2); six inactives there would have been equally consistent with "the direction is unreachable" and "the coupling is real but never yields rot 2 here" — a null that discriminates nothing. Swapping to a *known-active* cell made both outcomes informative at identical cost. Later the same session, choosing the full 36-cell sweep at s=1 over a 2-cell probe turned an expected null into a positive fact about the space: not "SW and SE didn't connect" but "exactly one cell in 36 connects". The cheap probe would have spent two renders and left the question open. The test is not "is this cheap" but "does every outcome move me".
22. **Automating a manual loop relocates the gate; it does not remove one.** Colby's ask on 2026-08-10 was "a lot of these sweeps are not decisions I am making — can we have a plan and let it go." The right read was not "remove approval" but "approve at the right altitude": the per-command gate had been protecting *nothing* for the mechanical steps (reset, settle, relaunch, resume a 520) while genuinely protecting the meaningful ones (is the oracle lying, is the model wrong). `run_sweep_queue.py` moved the gate from per-command to per-plan — one launch approves a declared campaign, and the harness-questioning conditions still halt and wait for a human. The diagnostic question when something feels like busywork: *which of these steps is a decision?* Everything else is a candidate for automation, and the answer names the new gate rather than deleting it. One firing.
23. **Unattended runs make the environment part of the harness.** Everything under test on 2026-08-10 was correct — the queue, the sweep, the oracle, the resume path — and the run still lost a cell, because the *machine* changed state: the screen locked, macOS throttled the occluded emulator's GPU, and a fixed sleep expired into a loading screen. Attended runs hide this class of failure, since a human is present precisely because they are watching the screen that would otherwise sleep. The moment a run is designed to proceed alone, the host's power management, display state, and window occlusion stop being background and become preconditions to declare (here: `caffeinate -d -w <pid>`, which also self-terminates with the run). Sibling of #21 — both are about asking what the run assumes before spending it. One firing, and it argues for `plan.md` item 4 (polling waits), which would absorb this class rather than trip on it. **Second firing 2026-08-21, one layer in**: the environment that broke the run was not the host's power state but the *application's* — a booted emulator with the app closed. `run_sweep_queue.py` never hit it because it resets before every sweep; every standalone script inherited the unstated precondition "the app is open, on the main menu." An unstated precondition is environment, and it belongs in the harness rather than in a human's habit. Two firings.

24. **An artifact that exists only as a conversation delivery is not state, and recording that a commit is owed reads to a check like having discharged it.** s20 closed cleanly — reflective pass run, `plan.md` noting "commit owed with offline tests", the handoff listing the miner and 43,375 port records as "delivered in the s20 conversation (not committed)". The close's step-1 check ("nothing derived this session is left orphaned") therefore *passed*, because the debt was written down. But the only copies were chat attachments plus an ephemeral sandbox, and the first durable write happened three days later, on 2026-08-21, only because the open-check went looking and only because that container happened to survive the idle gap. Had it been reclaimed, the honest answer would have been "gone; rebuild from the corpus." This is #12's shape at the artifact layer: the plan row and the decision not to commit share an origin — the same session wrote both — so their agreement was guaranteed and carried no information. The corpus itself, harvested straight to disk, was the only s20 product durable from birth; that asymmetry is the whole argument. Proposed fix, cheap enough to run every close: anything a canonical file *points at* must have a durable path, or the close names it at-risk rather than owed. One firing, but it nearly cost the project its most valuable instrument. **Second firing 2026-08-23 (s23), and it reached further than the first: the missing artifact was cited *as evidence* by shipped code.** Two `dumpsys window` captures — GraviTrax ~3s and ~33s after launch — were taken from the live AVD, found byte-identical, and that identity was written into `android.py` and a test module as the justification for a scope claim ("this guard cannot see which screen is showing"), pointing at `tests/fixtures/dumpsys_window_*.txt`. The glob resolved to the launcher/GraviTrax pair, which **differ**; the captures the sentence relied on existed only in the conversation. Caught by an adversarial panel that ran `cmp` on the pointer rather than reading past it. The compounding detail is that the same file argued, two paragraphs above, that a fixture written from memory "grades the author's memory of adb against itself" — the exact failure it was committing. Fix: both captures committed, with a test asserting the identity, so the claim rests on files. Generalises the s20 lesson from *artifacts* to *evidence*: a citation whose target does not contain the cited fact is worse than no citation, because it reads as having been checked. Two firings.

25. **A silent retry loop hides a missing binary.** A boot-wait written as `until [ "$(adb shell getprop sys.boot_completed 2>/dev/null)" = "1" ]; do sleep 3; done` spins forever when `adb` is not on `PATH`: the shell's "command not found" goes to the stderr the redirect discards, the substitution yields empty, and the comparison never succeeds. It presents as a hang with no output — the worst failure direction, because #17's lesson (rank guards by what a wrong answer would be believed to mean) has a third case beyond invented data and lost data: *no answer at all*, which costs a human's attention rather than a re-run. Two contributing causes worth separating: the redirect that suppressed the diagnosis, and the unbounded loop that had no way to give up. The fix is both — resolve the binary and prove it live before anything depends on it, then bound the wait. Compounding detail: `knowledge/environment.md` documents the `$ANDROID_HOME` fallback for the *emulator* binary and not for `adb`, and the same command applied it correctly to one and not the other. A gotcha documented for one instance of a class invites exactly that half-application (the `#12` *Classes* discipline from the global preferences, arriving from the other direction). One firing.

26. **A fixture set that shares a coincidence cannot see the bugs the coincidence masks.** Every course fixture in the suite placed its layer at world (0,0), so local and world coordinates coincided in every test — and a panel agent's mutation that swapped the two frames (the s21 defect's exact shape, one frame over) passed all 546 tests green, then reproduced the original false-ERROR symptom with the suite still green. One course with the layer translated — arranged so the frame confusion lands the starter on the measured-dead corner — now fails exactly one test under that mutation (verified by re-applying it). The general check: enumerate the coincidences the fixtures share (origins, zero rotations, single layers, default indices); each one is a blind spot the *whole* suite shares, which per-test review cannot find because every test is individually fine. Sibling of #12 — agreement guaranteed by construction — at the fixture layer. One firing, found by mutation testing in the s22 panel review.

27. **Output that will be pasted back needs a freshness stamp, or a stale paste is indistinguishable from a fresh one.** 2026-08-23 (s23): Claude was handed terminal output as the result of a just-launched run. It was the *previous* run's output, re-selected from scrollback. Every field was plausible — same cells, same predictions, same two upload failures — and the conclusion it invited was flatly wrong ("the retry I just shipped did not fire"). What caught it was not the data but a **prose detail**: the retry had changed the failure message from `upload failed:` to `upload failed after retries:`, and the paste used the old wording, which the current code cannot emit. Confirmed by reading `results.json` on disk, whose contents matched neither the paste nor Claude's model of events. This is `decisions.md`'s locked clipboard failure mode arriving by a different route — there, a stale share code invalidated a session of manual observations; here, stale scrollback nearly caused a working fix to be diagnosed as broken and re-engineered. The general shape: any artifact that crosses from a human's screen back into the session is undated by default, and *plausible* is the dangerous property, since an implausible paste gets questioned. Cheap fix adopted the same session — render commands now open with `date -u "+run started %H:%M:%SZ"`, so staleness is visible rather than inferred from writing style. Sibling of #5 (automate the loop the human is manually carrying) and of #12 (the paste and Claude's expectation shared an origin, so agreement carried no information). One firing.

28. **A canonical environment note is a measurement with a decay rate, not a constant.** `knowledge/environment.md` recorded, from s21 and explicitly "measured rather than assumed", that the device-VM bridge has **no network at all**. On 2026-08-23 it had network: `uv` fetched a CPython in 9s, pypi returned 200, `git ls-remote` succeeded. The note was true when written and false when read, and nothing in the file said which. It nearly cost the session a wrong architecture — the whole red-green loop was designed around that constraint. Two details make this more than "docs go stale". First, the *reason* the note existed (it was measured, against the s20 habit of assuming) is exactly what made it feel safe to trust. Second, the replacement is not "the VM has network" but a **decomposition**: the VM has network *and* caps calls at 45s *and* kills backgrounded processes — three independent facts the original note compressed into one, so when one changed the whole sentence became unreliable. The re-measurement cost about four commands at session open. Candidate rule: environment claims that gate architecture get re-measured at open rather than read, and get written as separable facts so a single change invalidates a single line. Sibling of #12 at the knowledge layer — reading a note about the environment is not the same act as observing the environment, and only one of them is evidence. One firing.
