Patterns noticed about how you and Claude work together on this project — frictions, recurring habits, things worth not losing. Numbered cumulatively across sessions; the numbers are stable references, so don't renumber when an observation moves.

This file has two sections. **Candidates** are patterns still being validated. **Promoted** are the ones durable enough to count as baseline expectations — a candidate promotes after it fires roughly three times across separate sessions (adjust the threshold in `workflow.md` if that doesn't fit your tempo).

A separate path runs to `decisions.md`: when an observation hardens into a commitment that constrains future work, it becomes a locked decision there, with the originating number noted for lineage. The two paths are independent — an observation can promote within this file, get locked as a decision, both, or neither.

**Update protocol.** The capture cadence lives in `workflow.md`; this file just holds the results. At session close: add new candidates, note any that fired again, promote the ones past the threshold, and retire candidates that have gone several sessions without firing.

32. **A mutation battery needs its control *asserted*, not observed — a broken battery reports reassurance.** 2026-08-24 (s25): a script applied 19 mutations to production code, ran the suite after each, and reported **0 of 19 caught** — including a control mutation that was known to be caught, because it reverted a fix whose regression test had been watched go red minutes earlier. The cause was one bad pytest flag (`-p no:randomly`, a plugin not installed): pytest exited with a usage error before collecting anything, printed no `FAILED` lines, and the script's parser read "no failures" as "the mutation survived". Every row was a false negative. Had the control not existed, the honest-looking conclusion would have been that 19 real coverage gaps were already covered — the failure direction that *invents* confidence rather than losing it (#17's ranking, at the meta level). This is #12's shape **inside the tool built to catch #12**, which is why it is its own entry: the battery's whole job is to prove a test can fail, and nothing was proving the battery could. Two fixes, and the second is the one that generalises: (a) a run that produces no test-summary line at all is a broken harness and must abort the battery, never be scored; (b) **the control's result must be an assertion that halts the run, not a row in the output table** — a human reading 19 rows will not notice that row 1 is wrong, and the script that prints the table is exactly the thing that should have refused to print it. Sibling of #27 (an artifact crossing back into the session is undated by default) in that both are about *plausible* output: the table looked exactly like a real result. One firing, and it would have blessed every gap the panel had just found. **First application 2026-08-24 (s26), and both rules earned their place.** A fresh battery over the pixel-stability work opened with a control (`FrameStability.__call__` returning `True` unconditionally) whose survival calls `sys.exit(1)` before any row is printed, and a summary-line regex that aborts the whole run if pytest emitted none. Neither fired — the harness was healthy — which is the point worth recording: **an un-fired guard is not a wasted guard**, and the s25 version of this table looked exactly as convincing while every row was a false negative. What the battery then found was real: 10 of 15 caught, one fixture coincidence explaining three survivors (see #26), and after the repair 17 of 17 including two mutations of the resampling filter that had not been in the first list. A third rule suggests itself and is not yet a rule: the first list of mutations is written against the code as the author understands it, so the mutation that matters most may be the one added *after* a finding changes that understanding — here, `BOX` → `BICUBIC` and `BOX` → `NEAREST` only became worth testing once the filter turned out to be load-bearing. **Second application 2026-08-25 (s27), and rule (a) fired for real.** The battery's very first run **aborted**: `pytest -q` prints no `====` banner, the summary-line regex missed it, and the script refused to score a run it could not read — with 730 green sitting on screen. That is precisely the s25 failure (parsing "no `FAILED` lines" as "survived") caught by the guard written after it, and the guard was catching *its own author's* bad regex rather than a broken suite. Two further findings. The third rule from s26 fired again and should now be promoted to a rule: the mutation that mattered most (`BOX` → `NEAREST`, which would have let the guard miss the frame it was built from) was only worth adding *after* a fixture coincidence revealed the resize branch was untested. And a new structural rule the session had to learn the hard way: **a `finally` does not survive `SIGTERM`.** An interrupted run stranded a mutation on disk; the next run's red-baseline abort caught it, but the `grep` that had "verified" the restore checked five of eighteen strings (#12 / *Classes*). Restoration is now three-layered — a stashed original, signal handlers, and an `atexit` check that re-reads the file — plus a pre-flight that runs every mutation string against the tree and aborts if any is present. 17 of 17 caught after repair.


33. **Offline tests verify the code; only the environment verifies the assumptions the fakes encode — and the environment needs its own committed check.** Raised by Colby 2026-08-25 (s27) after two consecutive render campaigns died without producing a measurement while the offline suite sat at 730 green: *"I think this is a hard part of having an external testing suite."* He is right, and the difficulty is specific rather than general. A fake **is** an assumption wearing a costume: `FakeAdb` returns a frame immediately, always the same size, never wedged, with the right app in front — four assertions about the world, encoded in the test harness, inherited by every test downstream and tested by none of them. So a test can prove the code is correct *given* the assumption, can never prove the assumption, and the assumption is what breaks. Adding offline tests makes the code more correct against the same unexamined premise. The two layers catch **disjoint** classes and neither substitutes for the other. Evidence is nine months of this project: every harness failure in `docs/refs/testing-against-a-live-app.md`'s ten-incident catalogue — the IME desync, the splash screen, the GPU throttle, the launcher, the SSL timeouts, the build tutorial, the graphics backend, plus the clipboard and scrollback pastes — happened with the suite green. **What the project got right without naming it:** the answer to an unverifiable assumption is not more tests but a *measurement inside the run* — the both-ends control, the local control, and four guards that refuse rather than answer. Worth stating as the honest accounting, because both halves are true: more campaigns have been voided by the harness than by the model being wrong, **and** the record has never once been corrupted, including by the two failures that produced a *positive* reading. The cost is paid in time, not in knowledge, which is exactly the trade #17's ranking is built to make. **The actionable half, and it is not built:** `scripts/preflight.py`. Four escalating diagnostic commands were hand-written in one evening and every one checked something that had actually broken; the graphics-error count alone would have caught the session's second failure before seven uploads and a void campaign. A check that lives in a human's habit is not a check. One firing, and the reference doc is the durable form.

34. **Asserting a mechanism during live diagnosis is a distinct habit from asserting one in code, and it fires hardest when the evidence is thinnest.** 2026-08-25 (s27): five times in one evening, all in conversation, all while diagnosing a broken emulator in front of a waiting human. (a) The build-tutorial failure's cause was written into `android.py` and a commit message as *fact* — "that tap lands on an empty slot and the app opens a new empty course" — when the evidence established only that no course was loaded; the log later revealed a second candidate, and the run that could have discriminated had already been truncated by a reboot, so the question is not open but **unanswerable**. (b) "Long-lived session degradation" was offered as the cause of the graphics failure; the log showed the errors began six lines after a *fresh boot*. (c) A portrait screencap was read as "the device is portrait" when the launcher was in front and phone launchers are portrait-locked — the number was right, the sentence attached to it was not. (d) An `emulator-user.ini` timestamp was pre-emptively labelled a weak hint, which was correct, and is recorded because it is the counter-example: declaring the strength of evidence *before* seeing it is what stopped it being promoted afterwards. (e) The stranded-mutation "verification" by partial grep, above. **Why the setting matters rather than the count.** Each of these was produced under a specific pressure — a human waiting, a broken system, and an explanation that would make the mess make sense. One firing as a named pattern, five instances within it.
